## Cloudflare CLI (`cf`) and vinext

`cf` (beta) is one CLI for the Cloudflare API and for Workers projects. It has no bundler of its own: it hands `dev` and `build` to Vite. This project runs **vinext** (the Next.js 16 API reimplemented on Vite) with the Cloudflare Vite plugin 2.0 beta. Docs: https://developers.cloudflare.com/cf/ and https://github.com/cloudflare/vinext.

> Not OpenNext, not Wrangler. OpenNext builds through Wrangler and has a reported conflict with `cloudflare.config.ts` (opennextjs-cloudflare #1407). Running `cf dev/build/deploy` in a project that has a Wrangler config makes `cf` write a new `cloudflare.config.ts` that ignores that config. Do not mix the two.

### Setup

```bash
npm install --global cf          # Node.js ≥ 22.18; Bun is not supported
cf auth login                    # in CI: CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID
pnpm create vinext-app@latest real-estate-tracker   # scaffold, Cloudflare target
```

- The scaffold should produce `vite.config.ts` and `cloudflare.config.ts`. If it produces `wrangler.jsonc` instead, stop: either convert with `cf migrate` or re-scaffold. Do not continue with a Wrangler config.
- For an existing Next.js app, `cf init .` detects Next.js and sets up vinext and `cloudflare.config.ts` (review the planned changes before confirming).
- `package.json` needs `"type": "module"`. Add `.cloudflare/` to `.gitignore`.
- Run `npx vinext check` to scan for known Next.js compatibility gaps.

### cloudflare.config.ts (shape)

```typescript
import { bindings, defineConfig } from "cf/config";

export default defineConfig({
  worker: {
    name: "real-estate-tracker",
    compatibilityDate: "<date written by cf init>",
    compatibilityFlags: ["nodejs_compat"],
    // entrypoint: as generated by the vinext / cf setup; don't hand-write unless setup omitted it
    env: {
      DB: bindings.d1({ name: "real-estate-tracker-db" }),
      KV: bindings.kv({ /* options: use TS completion or `cf docs search "kv binding"` */ }),
      MEDIA: bindings.r2({ /* options: as above */ }),
      CLERK_SECRET_KEY: bindings.secret(),
      GEOCODER_API_KEY: bindings.secret(),
      GEOCODER_PROVIDER: bindings.text("mapbox"),
      APP_URL: bindings.text("http://localhost:5173"),
    },
  },
});
```

- Builders: `bindings.d1 | kv | r2 | secret | text | json`. D1 options are `{ id?, name?, dev? }`. Confirm KV and R2 option names with TypeScript completion or the configuration explorer (https://developers.cloudflare.com/cf/projects/config-explorer/). Do not guess.
- `cf deploy` provisions missing resources for bindings that omit IDs and does **not** write the IDs back into the file. Local dev simulates all bindings; no IDs needed.
- `bindings.secret()` also makes `cf dev` warn about secrets missing from `.dev.vars`.
- For values that differ per environment use the function form `defineConfig(({ mode }) => ...)`. Vite accepts `--mode`; other framework commands reject it.
- Use `domains` under `worker` for custom domains.

### Reading bindings

```typescript
// lib/cloudflare.ts: the only file that imports cloudflare:workers
import { env } from "cloudflare:workers";
export function getEnv(): Env { return env; }
```

- `Env` is generated into `.cloudflare/types/index.d.ts` by the Vite plugin during `cf dev` / `cf build`, or by `cf workers types`. Add `.cloudflare/types` to tsconfig `include` explicitly (wildcards skip dot-directories).
- Call `getEnv()` inside request handlers, never at module top level.
- No `getCloudflareContext()`, no `getPlatformProxy()`, no `process.env` for bindings.

### What runs where

- `cf dev` runs the Vite dev server with the app inside workerd (Workers runtime). It prints the local URL (default `http://localhost:5173/`); `/cdn-cgi/local/explorer` opens Local Explorer to inspect bindings, logs, and traces. `cf dev` accepts no `--port`: set `server.port` in `vite.config.ts`.
- `cf build` writes Build Output to `.cloudflare/output/v0/` and needs no credentials. `cf deploy --dry-run` validates the build without credentials. `cf deploy` builds, uploads a version, and deploys. `cf previews deploy [name]` deploys a Worker Preview.
- Dev data lives in `.cloudflare/state/`. **`--local` on `cf d1/kv/r2` commands uses a different store** (`~/.config/cloudflare/state/v3` on Linux, `~/Library/Preferences/cloudflare/state/v3` on macOS), so migrations applied with `--local` may not be visible to `cf dev`. After applying migrations, check Local Explorer. If the tables are missing, try `--persist-to .cloudflare/state` (it uses `<dir>/v3`) or find the working invocation with `cf docs search` and record it in `progress-tracker.md`.

### vinext rules

- Supported and used here: App Router, React Server Components, Server Actions, route handlers, `proxy.ts`, `next/headers`, `next/navigation`, `next/cache` (`revalidatePath`, `revalidateTag`).
- Not used in v1: ISR, `revalidate`, `"use cache"` / Cache Components (incomplete in vinext), `next/image`.
- `runtime` and `preferredRegion` route config are ignored.
- `next/font/google` loads from Google's CDN at runtime (no self-hosting): the CSP must allow `fonts.googleapis.com` and `fonts.gstatic.com`.
- Never register `@vitejs/plugin-rsc` yourself: vinext does it when `app/` exists, and a duplicate fails the build. It only needs to be installed.
- Native Node modules (`sharp`, `satori`, `@napi-rs/canvas`, …) are not used.
- Run `npx vinext check` before upgrading vinext.
- Route folders whose name starts with `_` (including `__`) are Next.js **private folders** and are not routed: `app/api/__probe/route.ts` answers 404. Use a plain name for temporary probes.
- A brand-new route folder is only registered when the dev server starts; editing existing routes hot-reloads. Restart `pnpm dev` after adding one.

## Drizzle ORM + D1

```typescript
// lib/db/index.ts
import { drizzle } from "drizzle-orm/d1";
import * as schema from "./schema";
import { getEnv } from "@/lib/cloudflare";

export function getDb() {
  return drizzle(getEnv().DB, { schema });
}
```

```typescript
// lib/db/schema.ts (excerpt)
import { sqliteTable, text, integer, real, index } from "drizzle-orm/sqlite-core";

export const properties = sqliteTable("properties", {
  id: text("id").primaryKey(),
  ownerId: text("owner_id").notNull(), // Clerk user ID, no FK
  addressLine1: text("address_line_1").notNull(),
  priceCents: integer("price_cents").notNull(),
  bathrooms: real("bathrooms").notNull(),
  status: text("status", { enum: ["draft", "active", "sold", "off_market"] }).notNull().default("draft"),
  createdAt: integer("created_at", { mode: "timestamp_ms" }).notNull().$defaultFn(() => new Date()),
}, (t) => [index("properties_status_idx").on(t.status)]);
```

```typescript
// services/properties.ts: filtered read
const rows = await db.select().from(properties)
  .where(and(eq(properties.status, "active"), gte(properties.bedrooms, f.minBedrooms ?? 0)))
  .orderBy(desc(properties.createdAt))
  .limit(pageSize).offset(offset);
```

**Rules:**

- `getDb()` is called per request, inside services only.
- D1 has no interactive transactions: use `db.batch([...])` for atomic multi-statement writes.
- Foreign keys: ensure `PRAGMA foreign_keys` behavior by relying on D1's default (enabled) and `onDelete: "cascade"` for media.
- Generate migrations with `drizzle-kit generate`; apply with `cf d1 migrations apply <DATABASE_ID> [--local]` (remote by default; see the local-state note in the `cf` section).
- Free-text search uses `LIKE` on `address_line_1`, `city`, `postal_code` with escaped `%` and `_`.
- Generate IDs with `crypto.randomUUID()`.

## Cloudflare KV

```typescript
// lib/kv.ts
export async function cacheGetJson<T>(key: string): Promise<T | null> {
  try { return await getEnv().KV.get<T>(key, "json"); }
  catch (error) { console.error("[kv/cacheGetJson]", error); return null; }
}

export async function cachePutJson(key: string, value: unknown, ttlSeconds: number): Promise<void> {
  try { await getEnv().KV.put(key, JSON.stringify(value), { expirationTtl: ttlSeconds }); }
  catch (error) { console.error("[kv/cachePutJson]", error); }
}
```

```typescript
// list version (lib/kv.ts)
export async function getListVersion(): Promise<string> {
  return (await getEnv().KV.get("properties:list:version")) ?? "0";
}
export async function bumpListVersion(): Promise<void> {
  await getEnv().KV.put("properties:list:version", String(Date.now()));
}
```

`lib/kv.ts` also exports the key builders (`propertyListKey(version, queryHash)`, `propertyDetailKey(id)`) and `cacheDelete(key)`. Cache failures are swallowed and logged as `[kv/<helper>]`, never thrown.

**Rules:**

- Cache helpers swallow errors and return `null` (cache miss). KV holds no auth state in this project.
- `expirationTtl` minimum is 60 seconds. Use ≥ 60.
- KV is eventually consistent across regions: never use it for anything that must be immediately correct. Permissions come from Clerk (identity, role) and D1 (`owner_id`).
- Query hash: SHA-256 (Web Crypto) of the normalized, key-sorted filter JSON, hex-truncated to 32 chars.
- Rate limit counter: `ratelimit:{scope}:{userId}:{window}` with TTL = window (helper: `consumeRateLimit` in `lib/kv.ts`).
- Rate limits apply to geocoding and media upload only, keyed by Clerk user ID; a KV failure fails open. Both budgets are 60 calls an hour. Geocoding spends its counter in `services/geocoding.ts` only on a cache miss and reports `rateLimited` in its outcome, which `services/properties.ts` passes up as `GeocodeStatus` so the action can warn; media uploads spend theirs in `actions/media.ts` before the file is read (the action, not the service, knows the acting user when an admin acts on another owner's listing).
- Only the anonymous search and detail reads are cached (`services/properties.ts`). Owner/admin/draft reads bypass KV, and a cached detail is reused only while its status is `active`.
- Invalidation goes through `lib/events.ts` (`emitPropertyEvent`), never through inline `KV.delete` calls in actions. Every event bumps the list version; `updated`/`deleted` also delete `properties:{id}`.
- Development logs `[services/properties] cache hit|miss <key>` for every public read; that is the quickest way to confirm caching without a debug header.
- Inspecting the local KV store: `cf kv namespaces list --local` returns `[]` (the namespace is simulated), so use the simulated id: `cf kv keys list --namespace-id KV-real-estate-tracker --local --persist-to .cloudflare/state` (and `cf kv keys get <name> --namespace-id … --local --persist-to …`). List/detail entries expire in 60 s / 300 s, so read them promptly.

## Cloudflare R2 (binding)

```typescript
// lib/r2.ts
export async function putMedia(key: string, body: ReadableStream | ArrayBuffer, contentType: string): Promise<void> {
  await getEnv().MEDIA.put(key, body, { httpMetadata: { contentType } });
}

export async function getMedia(key: string): Promise<R2ObjectBody | null> {
  return getEnv().MEDIA.get(key);
}

export async function deleteMedia(key: string): Promise<void> {
  await getEnv().MEDIA.delete(key);
}
```

```typescript
// app/media/[id]/route.ts: streaming response
// The row lookup and access rule live in services/media; the resolver runs only for a non-active parent.
const target = await getForServing(id, getOptionalUser);
if (!target) return new Response("Not found", { status: 404 });

const object = await getMedia(target.r2Key);
if (!object) return new Response("Not found", { status: 404 });
return new Response(object.body, {
  headers: {
    "Content-Type": object.httpMetadata?.contentType ?? "application/octet-stream",
    "Cache-Control": target.isPublic ? "public, max-age=3600" : "private, no-store",
    "X-Content-Type-Options": "nosniff",
  },
});
```

**Rules:**

- Use the **binding**, not the S3 API. No R2 access keys in the app.
- Key format is always `properties/{propertyId}/media/{mediaId}`.
- Stream bodies; never buffer files larger than needed.
- Delete the R2 object whenever the DB row is deleted, and delete all objects with prefix `properties/{id}/media/` when a property is deleted (use `list({ prefix })`).

### Uploads through Server Actions

```typescript
// actions/media.ts (client calls it directly, once per file)
const file = formData.get("file");
if (!file || typeof file === "string") return fail("Choose a file to upload.");

// services/media.ts
await r2.putMedia(key, await file.arrayBuffer(), file.type);
const [row] = await db.insert(propertyMedia).values({ ... }).returning();
```

- Vinext accepts a `File` inside a `FormData` argument to a Server Action. `formData.get()` returns `File | string | null`, so narrow with `typeof file === "string"`; `instanceof File` is not reliable across the worker/client boundary.
- Validate `file.size` and `file.type` **before** `arrayBuffer()`, so an oversized upload is rejected without being buffered.
- One Server Action call per file, issued from a client loop, gives each file its own pending row and error message; a single multi-file call can only report one status for the batch.
- Put into R2 first, insert the row second, and delete the object in the insert's `catch` so storage never keeps a file the database does not know about.
- **Server Action bodies default to 1 MB** in Next.js and in vinext (it enforces the limit before the action runs). `next.config.ts` raises `experimental.serverActions.bodySizeLimit` to `"12mb"`, one file per call against the 10 MB cap in `validations/media.ts`; without it, any photo between 1 MB and 10 MB fails with a body-size error instead of reaching the action. Keep the two numbers in step if the media cap changes.

## Vitest and Miniflare (tests)

`pnpm test` is `vitest run` over `vitest.config.ts`; test files live in `tests/` and use `tests/support/` for the harness.

- Tests run in **Node**, not workerd. Two aliases make the server modules importable there: `@/` → the repo root, and `cloudflare:workers` → `tests/support/cloudflare-workers.ts`, a proxy over the current test environment. `lib/cloudflare.ts` is the only reader of that module, so the alias is enough for `lib/db`, `lib/kv`, `lib/r2` and everything above them.
- `@cloudflare/vitest-pool-workers` is deliberately not used: it needs a Wrangler config, which this project does not have. Each test file boots its own in-memory **Miniflare** instead (`tests/support/worker.ts`): D1, KV and R2 bindings named `DB`, `KV` and `MEDIA` with the committed migrations applied, and `resetTestWorker` empties the tables, the KV keys and the bucket between cases.
- **Miniflare 5 beta takes the worker-array options, not the v3/v4 flat ones.** `{ d1Databases, kvNamespaces, r2Buckets, script, compatibilityDate }` fails with a Zod "unrecognized keys" error; the shape is `{ workers: [{ config: { name, compatibilityDate, compatibilityFlags, manifest: { mainModule, modules }, env: { DB: { type: "d1" }, KV: { type: "kv" }, MEDIA: { type: "r2" } } } }] }`. `getD1Database` / `getKVNamespace` / `getR2Bucket` then return workerd proxies, and Drizzle's `d1` driver (including `db.batch`) works against them unchanged.
- Mock the geocoder with `vi.mock("@/services/geocoding")` in service tests so no case reaches geocod.io.
- Auth cases mock the Clerk server module with `vi.hoisted` (a `vi.mock` factory is hoisted above ordinary constants) and feed `sessionClaims.metadata.role`; the pure helpers in `lib/auth/roles.ts` need no mock. The list cache key is asserted through `search()` and `worker.kv.list({ prefix })` rather than by exporting the private key builder.
- The documented manual pass lives in `context/smoke-checklist.md`: sign up → create → upload → public view → delete, plus the role/IDOR and rate-limit checks.
- `package.json` pins `vinext`, `cf`, `@types/node` and `@cloudflare/vite-plugin` to exact versions on purpose: a dependency written as `latest` is re-resolved by every `pnpm add`/`pnpm install`, which once pulled a new vinext in while adding a dev dependency.

```typescript
    "/(api|trpc)(.*)",
  ],
};
```

```typescript
// in every protected page, route handler and Server Action
const { isAuthenticated, userId } = await auth();
if (!isAuthenticated) await auth.protect();
```

Use the matcher `clerk init` generates if it differs. Verify the protection actually blocks signed-out requests.

### Secrets and environment

- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` is inlined at build time: it must be present in `.env.local` (or CI env) when running `cf build` / `cf deploy` **and** when `cf dev` starts, because the value is baked into the client bundle at server start. Changing it requires restarting `cf dev`.
- `CLERK_SECRET_KEY` is declared with `bindings.secret()` in `cloudflare.config.ts`. That declaration is what makes the value visible — a value in `.dev.vars` alone is not. Confirmed 2026-10-27: with the secret only in `.dev.vars`, Clerk threw "Missing secretKey" on every request.
- A first `cf deploy` of a Worker with a declared secret needs the value up front: `cf deploy --secrets-file .dev.vars` (the file is already in `SECRET_NAME=value` form and is gitignored).
- Clerk's keyless mode may be used for the first local run; link a real Clerk application before any deploy.
- Development and production are separate Clerk instances: keys, session-token customization, and role metadata must be set up again for production.

### Verified behaviour (2026-10-29, feature 10)

- **Sign-up/sign-in with a `+clerk_test` address:** Clerk accepts the code `424242` for both email verification and client-trust verification, so no mailbox is involved. A UI sign-up is: email + password → `/sign-up/verify-email-address` → code → `/dashboard`.
- **Client trust (`needs_client_trust`):** a `signIn.create({ identifier, password })` from a fresh browser profile returns `needs_client_trust` instead of `complete`. Send a code with `prepareFirstFactor({ strategy: "email_code", emailAddressId })` and then `attemptFirstFactor({ strategy: "email_code", code: "424242" })` — calling `attemptFirstFactor` before `prepareFirstFactor` fails with "You need to send a verification code before attempting to verify."
- **Setting a test password from the CLI:** `clerk api /users/{id} -X PATCH -d '{"password":"…"}'`. Procedural passwords must be **15 characters or more** (`form_password_length_too_short`), even when the sign-up form accepts fewer.
- **Session tokens live 60 s** on this instance, so an idle tab cycles through `https://<instance>.clerk.accounts.dev/v1/client/handshake?...&__clerk_hs_reason=session-token-expired...` URLs and a tab can be mid-handshake at any moment. A `curl` check must send `Accept: text/html` and keep a cookie jar (`-c/-b`), or every document request looks like a 307 to Clerk.
- **`auth.protect()` with no argument builds an `https://` sign-in URL in local dev** (Clerk resolves the env sign-in URL against an origin it reports as `https://`), which the plain-http dev server cannot serve. Pass a relative `unauthenticatedUrl: "/sign-in?redirect_url=<page>"` instead — see `requirePageUser` in `lib/auth/current-user.ts`.
- **Wrap Clerk widgets in `ClientOnly`.** They render nothing until clerk-js reports `loaded`; if clerk-js is ready before React hydrates, the first client render differs from the server output and React reports a hydration mismatch on the auth pages and the navbar.

**Rules:**

- Never write password hashing, session storage, or auth cookies. Never add a `users` table.
- `auth()` is async; call it only in server code, and only on routes covered by the `proxy.ts` matcher.
- Never trust role or user ID from the client. Derive from `auth()`.
- Session claims can be stale for up to about a minute after a role change; use `getFreshRole` before deletes.
- Do not copy Clerk profile data into D1. Read it from Clerk when needed.
- Mock `@clerk/nextjs/server` in unit tests.
- **vinext + Clerk (known issue, cloudflare/vinext#4221):** `cf dev` crashes at startup with `ReferenceError: require is not defined` from `@clerk/nextjs/dist/esm` because the ESM build calls bare `require()` in four modules (`runtime/node/safe-node-apis.js` for `node:fs`/`node:path`, `app-router/server/auth.js` and `currentUser.js` for `server-only`, `client-boundary/hooks/usePathnameWithoutCatchAll.js` for `next/navigation`), and the dev module runner evaluates them unbundled inside workerd. Reproduced on vinext 1.3.1 with `@clerk/nextjs` 7.9.21 — neither is fixed upstream.
- **The `clerkRequireToImport()` plugin in `vite.config.ts` is already the fix.** It rewrites those bare calls into hoisted `import * as … from "x"` for server environments, dev only (`apply: "serve"`). `cf build` and `cf deploy` never need it: the production bundler rewrites the calls itself. Keep the plugin until a vinext or Clerk release removes the bare `require()`s.
- `clerk init` generates a generic Next.js setup. Do not let it add a Wrangler config or OpenNext files.

## Geocoder (geocod.io, API v2)

```typescript
// lib/geocoder/geocod.ts
const params = new URLSearchParams({
  street, city, state_province, postal_code, country: "USA", limit: "1",
});
const res = await fetch(`https://api.geocod.io/v2/geocode?${params.toString()}`, {
  headers: { Authorization: `Bearer ${getEnv().GEOCODER_API_KEY}` },
  signal: AbortSignal.timeout(4000),
});
if (!res.ok) return null;
// results[0].location.lat / .lng, results[0].formatted_address
```

**Rules:**

- Base URL is `https://api.geocod.io/v2/`; the version prefix is required. Send the key in the `Authorization: Bearer` header, never `?api_key=`, so URLs and error text never carry it.
- Send components (`street`, `street2`, `city`, `state_province`, `postal_code`, `country`), not a concatenated query. `country` accepts `USA` | `Canada` | `Mexico` | `GB`; anything else is not geocoded (return `null`) rather than being resolved as a US address.
- Results are ordered most-accurate-first, so `results[0]` is the pick. No results means `null`.
- Implement the `Geocoder` interface; selecting a vendor happens only in `lib/geocoder/index.ts` (`GEOCODER_PROVIDER`, default `geocod`). `GEOCODER_PROVIDER` is a text binding and `GEOCODER_API_KEY` a secret binding in `cloudflare.config.ts`; the key lives in `.dev.vars` locally and in the deployed secret otherwise. Never in `.env.local`, never in a client bundle.
- 4 s timeout; non-2xx, timeout, missing key or no match returns `null` after logging the status or error name only (no address, no key).
- Always check KV `geocode:{addressHash}` first (`cacheGetJson`/`cachePutJson`, 30-day TTL). Normalize (trim, lowercase, collapse spaces) before hashing with `sha256Hex`.
- Re-geocode on update only when an address field actually changed; otherwise keep the stored coordinates.
- Rate limit provider calls with `consumeRateLimit("geocode", userId, 60, 3600)` before the fetch. Cached hits do not count, and the check fails open.

## shadcn/ui

The project uses the classic **Radix**-based components (the unified `radix-ui` package) with the `new-york` style and CSS variables.

- `components.json` is committed and points at `app/globals.css`. Adding a component: `pnpm dlx shadcn@latest add <name> -y`, then run the token check below.
- **`shadcn init` does not work non-interactively here.** With no TTY it waits on a prompt and never returns; it also detects Vite rather than the Next-on-vinext setup. The committed `components.json` is the result of doing that step by hand. Do not re-run `init`; edit `components.json` instead if the config must change.
- `add` writes `import { cn } from "cn"` and installs the `cn` npm package, plus `next-themes` for `sonner`. Both are unapproved dependencies: rewrite the import to `@/lib/utils` and drop `next-themes` (`sonner.tsx` is pinned to `theme="light"`).
- **Always check a newly added component for token drift** before committing it: replace raw colour classes (`text-white`, `bg-black/50`), rewrite shadcn's neutral `bg-accent` hovers to `bg-surface-secondary`, and use `bg-surface` for content surfaces where the generator writes `bg-background` or `bg-transparent`. The adjustments already made are listed in `ui-registry.md`.
- Do not edit generated primitives for anything other than mapping classes to project tokens.
- Use `Form`-style composition with `react-hook-form` + Zod resolver for the property form.
- Use `sonner` for toasts, `AlertDialog` for destructive confirms (delete property, delete media).
- Overlay scrims use `bg-overlay` (`--color-overlay`), not `bg-black/50`.

### Testing overlays

Radix keeps a dialog, sheet or alert dialog mounted until its exit animation fires `animationend`. In a headless or **hidden** browser tab the document's animation timeline does not advance, so `document.timeline.currentTime` stays `0`, the animation never ends, and the overlay stays in the DOM even though `data-state` is `closed`. That is an artefact of the test environment, not a bug: inject `*,*::before,*::after{animation:none!important}` before interacting when you need to assert that an overlay closes.

The same hidden-tab limitation swallows focus events: `element.focus()` followed by `element.blur()` fires neither `blur` nor `focusout`, so a save-on-blur handler never runs. To test one, set the value with the native `HTMLInputElement.prototype.value` setter and dispatch `new FocusEvent("focusout", { bubbles: true })`; that reaches React's `onBlur`.

## Security headers and CSP

Declared once in `next.config.ts` with `headers()`, applied to every route (`source: "/(.*)"`), not in `proxy.ts`. vinext resolves the rule at server start and applies it to HTML, `/api/*` responses and Clerk's handshake redirects (development and `vite preview` both log `✨ Parsed 1 valid header rule`).

- Headers: `Content-Security-Policy`, `Strict-Transport-Security` (1 year, includeSubDomains), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb, interest-cohort all off).
- The CSP must keep, or Clerk/Turnstile/fonts break: `https://*.clerk.accounts.dev` and `https://*.clerk.com` in `script-src`/`connect-src`/`frame-src`/`img-src`, `https://*.protect.clerk.com` in `script-src`/`frame-src` and `https://*.protect.clerk.com:*` (port wildcard required) in `connect-src`, `https://challenges.cloudflare.com` (Turnstile) in `script-src`/`connect-src`/`frame-src`, `https://img.clerk.com` in `img-src`, and `https://fonts.googleapis.com` / `https://fonts.gstatic.com` in `style-src` / `font-src` for `next/font/google`.
- `'unsafe-inline'` in `script-src` and `style-src` is required by the App Router and Clerk's CSS-in-JS. `'unsafe-eval'` and the Vite HMR websocket (`ws://localhost:*`) are added only when `NODE_ENV !== "production"`.
- Editing `headers()` requires a `pnpm dev` restart; the policy is resolved at startup, not per request.
- A production Clerk instance on `clerk.<domain>` needs that exact host added in feature 19 — the wildcards above are what the dev instance uses.

Verify with `curl -s -D - -o /dev/null http://localhost:5173/properties | grep -i content-security-policy` and, for enforcement, add a `securitypolicyviolation` listener and load a foreign script/image in the browser.
